# Engineering v2.2.6 exact release traceability

This specification is the shared, population-free source for the generated
v2.2.6 release matrix. `release/v2.2.6-requirements.json` is authoritative for
the complete requirement identifiers and their executable mappings. The matrix
generator reads exact Git objects, names the commit and tree, and fails closed
when a mapping, referenced blob, test selector, or required evidence is absent.

## External owner authority

Engineering validates host-owned approval and intent receipts. Candidate Git
cannot create owner approval, signer authority, exceptions, or audit identity.

## Predecessor and survival completeness

Every active approved outcome has an explicit predecessor, carry-forward, or
owner-authorized disposition. The controller baseline cannot be omitted;
exceptions remain external and replacement requires independent equivalence.

## Refreshed intent impact and continuity

Preparation plus refreshed/current exact checkpoints determine intent impact.
New, renamed, omitted, and previously unrepresented material paths fail closed.
The owner-intent digest remains bound through execution, handoffs, completion,
and compaction.

## Typed evidence and independent acceptance

Evidence classes are ordered. Proxy, design, unit, and integration evidence
cannot satisfy a higher class. Exact-artifact acceptance requires an auditor
independent of architect, implementer, and writer.

## Exact release and installation

Release tokens, source bundles, install receipts, retries, rollback, and public
exports bind exact commits, trees, deterministic Git-object bytes, and exact or
absent mutation preimages. Historical receipts remain readable but are never
silently upgraded.

## Non-circular bootstrap and host trust

The one-time v2.2.6 bootstrap is governed by installed v2.2.5, recorded owner
approval, and distinct semantic and technical exact-artifact audits. It does
not call its own post-activation gate. After activation, trust and intent state
live at a host-owned private boundary outside candidate Git and survive restart.

## Post-activation all-outcome binding

Immediately after activation, every recorded approved outcome category,
including product releases and other accepted owner outcomes, must be imported,
bound, and completeness-checked before v0.6.1, frontend, plugin, headless, or
other downstream implementation dispatch. Populated outcomes stay outside Git.

## Native outcome and routing proof

Native harness capability is proven, not inferred from hooks or MCP. Real
Codex and Claude fan-out/fan-in without prompt steering is required where owner
intent asks for it. Routing disclosure retains typed model, effort/reasoning,
owner override, execution target, and scope, using Unknown when unprovable.

## v0.6.0 incident regression

A policy kernel plus unit evidence cannot self-exclude executable native graph,
autonomous fan-out/fan-in, or no-prompt-steering outcomes. The release gate must
reject that proxy-only shape.

## Isolation and paired distribution

Ambient Git routing and provider credentials cannot redirect project identity
or child execution. Internal and sanitized public artifacts retain byte-parity
for their shared manifest while audience-specific and public-only artifacts are
explicitly present and validated.

## Generated matrix and evidence gates

The deterministic generated report maps each authoritative requirement through
lifecycle state, design, contract, runtime behavior, negative test, native
evidence, and exact artifact identity. Omission, Unknown required evidence, or
insufficient proxy evidence blocks the applicable gate. Post-activation Unknown
does not pre-bind private outcomes, but it blocks every dependent dispatch.
